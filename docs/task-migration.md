## Порядок

1. Перед каждой партией проверь актуальную ветку `practice`, полный набор файлов и Git-хеши рабочего набора и исходной копии. При расхождении или наличии сохранённой попытки не меняй её автоматически. На локальной машине отдельно проверь `git status` и сохрани незакоммиченные решения.
2. Разбери условие, исходник, подсказку и проверочный UI каждой задачи. Зафиксируй учебную цель, обязательные этапы, исходные данные, публичный контракт и признаки правильной работы.
3. Определи подход:
   - короткие хуки: решение и готовый потребитель в одном файле, если это не скрывает контекст;
   - компоненты: минимальная заготовка или исходный UI согласно заданию;
   - многофайловые упражнения: сохраняй границы учебной задачи, данные, стили и API;
   - review: отдельно оцени исполняемость исходника, сохраняй его ошибки и неизменённый текст при технической адаптации;
   - консольные задачи: не требуют React, если он не нужен для отдельного этапа.
4. Перенеси рабочий набор рядом с `task.md`, обнови ссылки, относительные импорты и `starter/`. Удаляй старые посредники и пустые служебные папки только после проверки их использования. Подключи браузерный рабочий компонент через `React.lazy` в существующем реестре. Сохраняй id, название и категорию, если исходная классификация верна.
5. Проведи проверку на отдельной ветке или точном кандидате коммита: сборка, ESLint обычного кода, ссылки, чистые исходные копии, сохранённые источники, браузерный запуск и сценарии проверки. Для review сравни диагностики до/после и не исправляй ожидаемые учебные дефекты. При сетевых упражнениях отделяй доступность API от корректности инфраструктуры.
6. Проверь глазами ученика: можно ли начать работу сразу после чтения условия, понятно ли назначение предоставленных файлов, не раскрыта ли реализация. Если задача не отвечает этим критериям, доработай её до публикации.
7. Публикуй проверенные партии в `practice` атомарно, без force-push. Не объединяй с `main` без отдельного решения.

## Очерёдность партий

- Первая партия: короткие хуки с простым демонстрационным UI. Начать с небольшого набора (3–5), проверить подход, затем продолжить.
- Вторая партия: простые компоненты и готовые исходные данные. Не объединять файлы только ради числа файлов.
- Третья партия: сложные компоненты и хуки с несколькими сценариями, сетевыми запросами, таймерами или подписками; проверять исходные этапы и очистку эффектов.
- Четвёртая партия: исполняемые code review; затем задачи с текстовыми исходниками. Не запускать автоматически синтаксически некорректный материал.
- Отдельно: `timeout-basics` (рабочий набор уже отличается от starter) и `00-sandbox-guide` (готовый пример и архив `2026-08-20`). Не перезаписывать их в процессе миграции.

Размер партии определяет сложность задач. Массовое переименование, glob-реестр, дополнительные runtime-зависимости, изменение tsconfig и автоматический сброс не являются предварительными условиями миграции.

Ограничения пилота: Error Boundary изолирует ошибки рендеринга, но не все ошибки выполнения; при ошибке трансформации Vite может потребоваться ручная перезагрузка. Общий ESLint на проверенном снимке возвращает 4 ошибки и 2 предупреждения в намеренно дефектных review-файлах. Автоматизированная техническая проверка не заменяет пользовательскую UX-приёмку.
