## Порядок

1. Перед каждой партией проверь актуальную ветку `practice`, полный набор файлов и Git-хеши рабочего набора и исходной копии. При расхождении или наличии сохранённой попытки не меняй её автоматически. На локальной машине отдельно проверь `git status` и сохрани незакоммиченные решения.
2. Разбери условие, исходник, подсказку и проверочный UI каждой задачи. Зафиксируй учебную цель, обязательные этапы, исходные данные, публичный контракт и признаки правильной работы.
3. Определи подход:
   - короткие хуки: решение и готовый потребитель в одном файле, если это не скрывает контекст;
   - компоненты: минимальная заготовка или исходный UI согласно заданию;
   - многофайловые упражнения: сохраняй границы учебной задачи, данные, стили и API;
   - review: отдельно оцени исполняемость исходника, сохраняй его ошибки и неизменённый текст при технической адаптации;
   - консольные задачи: не требуют React, если он не нужен для отдельного этапа.
4. Перенеси рабочий набор рядом с `task.md`, обнови ссылки, относительные импорты и `starter/`. Удаляй старые посредники и пустые служебные папки только после проверки их использования. Подключи браузерный рабочий компонент через `React.lazy` в существующем реестре. Сохраняй id, название и категорию, если исходная классификация верна.
5. Проведи проверку на отдельной ветке или точном кандидате коммита: сборка, ESLint обычного кода, ссылки, чистые исходные копии, сохранённые источники, браузерный запуск и сценарии проверки. Для review сравни диагностики до/после и не исправляй ожидаемые учебные дефекты. При сетевых упражнениях отделяй доступность API от корректности инфраструктуры.
6. Проверь глазами ученика: можно ли начать работу сразу после чтения условия, понятно ли назначение предоставленных файлов, не раскрыта ли реализация. Если задача не отвечает этим критериям, доработай её до публикации.
7. Публикуй проверенные партии в `practice` атомарно, без force-push. Не объединяй с `main` без отдельного решения.

## Этапы по учебным группам

Группу определяет результат, который автор просит от ученика в исходном условии. Один этап охватывает согласованную группу целиком.

| Характер задачи | Что сдаёт ученик |
| --- | --- |
| Рефакторинг · ревью кода | Разбор выданного кода с объяснением проблем и правками в объёме исходного условия. |
| Рефакторинг · исправление поведения | Исправленный существующий компонент, выполняющий конкретное требование автора. Распределение двух групп — в [каталоге рефакторинга](../src/tasks/review/README.md). |
| Создание компонента | Компонент с заданным интерфейсом и поведением. Если условие включает запрос, вывод списка и последующее выделение хука, сохрани все этапы вместе. |
| Создание хука | Хук с указанным контрактом. Если автор требует использовать его в компоненте, это входит в задачу. |
| Реализация функции или другой самостоятельной логики | Функция либо алгоритм с поведением из условия. В проекте такие упражнения есть в `js-basics/`. |

Для каждой задачи отдельно определи, с чем взаимодействует код (например, API, таймер, событие браузера) и как ученик проверяет результат: в интерфейсе, в консоли или разбором кода без запуска. Сохрани способ, предусмотренный условием. Если для ревью достаточно чтения компонента, наличие JSX само по себе не требует отдельного экрана. Если нужно получить данные и показать список, сохрани взаимодействие с API и проверку списка в UI.

Внутри группы можно начать с показательной задачи и переносить остальные небольшими партиями. После согласования шаблона и структуры выполняй весь объём группы без промежуточных согласований по файлам или партиям. Если отдельное упражнение требует решения автора, зафиксируй вопрос и продолжи доступные задачи этой группы.

В `timeout-basics` рабочая попытка перенесена в корень упражнения с сохранением её кода и отдельной исходной копии. Вводный `00-sandbox-guide` содержит готовый пример и архив `2026-08-20`.

Размер партии определяет сложность задач. Массовое переименование, glob-реестр, дополнительные runtime-зависимости, изменение tsconfig и автоматический сброс не являются предварительными условиями миграции.

Ограничения пилота: Error Boundary изолирует ошибки рендеринга, но не все ошибки выполнения; при ошибке трансформации Vite может потребоваться ручная перезагрузка. Общий ESLint на проверенном снимке возвращает 4 ошибки и 2 предупреждения в намеренно дефектных review-файлах. Автоматизированная техническая проверка не заменяет пользовательскую UX-приёмку.


## Создание компонентов — согласованная структура

Во всех 34 задачах рабочие файлы лежат рядом с условием. Песочница загружает экран непосредственно из папки задачи.

- В начале task.md укажи первое действие и ссылку на файл, где ученик его выполняет. Далее сохрани исходные требования, подсказки и сценарий проверки.
- Положи рабочий компонент с его JSX рядом с условием и подключи его к песочнице заранее. Для создания с нуля дай минимальную заготовку. Для доработки сохрани предоставленную разметку и поведение.
- Если компонент проверяется через props, оставь готовый пример его использования. В checkbox-list первым открывают CheckboxList.tsx. Родитель уже передаёт items, value и onChange.
- Для задачи с несколькими рабочими файлами обозначь порядок и роль каждого. В mocked-data-list ученик реализует асинхронный мок в api.ts и вывод в компоненте. В adaptive-overflow-menu уже предоставлены Menu, Dropdown, MenuItem, данные и стили; сохрани границы исходного интерфейса.
- В starter/ храни версию редактируемых файлов для повторной попытки. Общие готовые данные и неизменяемую обвязку достаточно хранить в одном месте. Сохрани существующие попытки и проверь расхождения перед переносом.
- Эталон для самопроверки размещай отдельно в solution.tsx или solution/ по числу модулей решения. Открывать его предлагается после выполнения задания.
- Способ проверки берётся из условия. Для controlled-uncontrolled-inputs нужны одновременно поля в браузере и вывод их значений в консоль. Реальный API, учебный мок и локальные данные сохраняют свою роль в исходном сценарии.

## Хуки — согласованная структура

Для каждой задачи укажи рабочий файл непосредственно в начале task.md. В коротком примере хук и вызывающий компонент могут находиться рядом в одном файле. Если демонстрация занимает больше места, рабочим остаётся файл хука, а песочница подключает готовый пример. В starter/ лежит копия редактируемого файла, отдельное решение открывается после самостоятельной попытки.

- Если результат виден или действие выполняется в UI, сохрани предусмотренную условием демонстрацию. Например, useFocus проверяют вводом в поле после нажатия кнопки, а useClickOutside — кликами внутри и снаружи элемента с наблюдением сообщения в консоли.
- Если достаточно реализовать контракт или увидеть вызов обработчика, не требуй от ученика писать UI. В useKeyPress для проверки достаточно клавиши и сообщения в консоли. Существующий пример в песочнице уже вызывает хук в React.
- Сценарии эффекта могут использовать оба способа: в useEffectOnce кнопка управляет монтированием, сообщения показывают запуск и очистку.

Все 29 папок hooks используют рабочий файл рядом с условием. Изменение рабочего файла обновляет подключённый пример без выбора попытки.
