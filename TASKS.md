# Работа с учебными задачами

## Для ученика

1. Выбери раздел и прочитай `task.md`.
2. Открой рабочий файл по ссылке в условии. В новом формате он лежит рядом с `task.md`, в старом — в `attempts/current/`.
3. Реализуй задание и проверь результат по условию: в терминале или в [браузерной песочнице](./README.md#как-проверить-задачу-в-браузере). Если после исправления синтаксической ошибки экран не восстановился, перезагрузи страницу.
4. Если нужна помощь, открой `hint.md`, если он предусмотрен.

### Файлы нового формата

```text
<папка-задачи>/
├── task.md
├── UseToggleTask.tsx   # рабочий файл (имя зависит от задания)
├── starter/
│   └── UseToggleTask.tsx
├── hint.md             # необязательно
└── attempts/           # появляется при сохранении попыток
    └── YYYY-MM-DD/
```

В многофайловом задании рядом с условием находятся все рабочие файлы. `starter/` хранит их исходные версии. Не редактируй `starter/` при решении.

### Как сохранить прохождение и начать заново

Если нужна текущая попытка, сначала скопируй все её рабочие файлы с сохранением относительных путей в новую папку `attempts/YYYY-MM-DD/`. Для старого формата скопируй весь набор из `attempts/current/`. Не перезаписывай сохранённые попытки: при совпадении даты добавь суффикс, например `2026-08-20-2`. По желанию добавь `solution.md` с объяснением решения.

Чтобы начать заново, восстанови исходные версии рабочих файлов из `starter/`. Дополнительные файлы, созданные при решении, сначала сохрани и затем убери из рабочего набора, если они больше не нужны. Не удаляй архивы.

## Для автора

### Категория и условие

- Категорию определяет учебная цель. Чистый JavaScript — `js-basics`, создание экрана — `components`, самостоятельная реализация хука — `hooks`, разбор готового кода — `review`.
- Многошаговая задача «создать экран → загрузить данные → выделить хук» остаётся целиком в компонентах. Не меняй порядок этапов, исходные данные, контракты, UI или учебные ошибки ради унификации.
- В начале `task.md` дай прямые ссылки на рабочие файлы. Укажи, что уже готово, что нужно реализовать, где увидеть результат и как проверить все требования. Не добавляй требований, которых нет в исходной задаче.

### Рабочий код

- Минимальный и самодостаточный код, а не минимальное число строк. Ученик должен понимать, где писать решение, как используется его код и что произойдёт после сохранения.
- Если короткий хук используется в готовом JSX, размещай их в одном рабочем файле, как в [useToggle](./src/tasks/hooks/use-toggle/task.md) и [usePrevious](./src/tasks/hooks/use-previous/task.md).
- Если UI является учебной целью, не реализуй его за ученика. Данные и простой контекст применения можно разместить рядом. Выделяй отдельные файлы, когда это нужно для исходной задачи или действительно улучшает читаемость. Например, [асинхронный мок](./src/tasks/components/mocked-data-list/task.md) требует отдельного `api.ts`.
- Для консольной задачи не добавляй React. Сохраняй возможность проверить результат командой из условия.
- Готовые типы описывают контракт, если их самостоятельное написание не является целью. Не предоставляй ту часть типизации, которую требуется реализовать.
- Не используй фиктивные обработчики, `any`, приведения типов или технические посредники только для подавления ошибок. Предпочитай естественную пустую заготовку: `return null` для компонента или `return undefined`, если это допустимый результат функции. Если контракт требует результат, а реализации пока нет, допустим пояснённый `throw new Error(...)`, который обрабатывает песочница.
- Если техническая конструкция необходима (например, `void` для ещё не использованного аргумента), объясни рядом: зачем она нужна, чего не реализует и что заменить. Поясняй непривычные типы и связь частей кода. Не комментируй очевидный синтаксис и не подсказывай решение.
- Общая обработка ошибок и загрузка — ответственность песочницы, а не ученика. Подключённый UI должен использовать рабочий код ученика, не копию из `starter/` и не готовое решение.

### Code review

Сначала определяй учебную цель по исходному заданию. Для интервью и статического рефакторинга сохраняй исходный код в обычном рабочем файле рядом с `task.md`, без адаптации, комментирования, исправления ошибок или добавления UI. В `starter/` хранится точная исходная копия. Если исходник состоит из нескольких файлов, сохраняй их границы; не выдумывай отсутствующий код. Храни отдельный источник только если он содержит сведения, которых нет в рабочем наборе.

Для таких задач в реестре достаточно id, названия и категории; рабочий код не импортируется приложением. Намеренно дефектные изолированные файлы не проверяй как код приложения. При необходимости точечно исключи их из общего ESLint, не меняя правила для остального кода. Проверяй сохранность исходника, ссылки, доступность задания и качество ответа. Отдельный просмотрщик исходника и обязательный `review.md` не нужны.

Рекомендуемый ответ — `solution.tsx` (или другой исходный язык), для нескольких файлов — `solution/`. Для вопросов только на анализ допустим `solution.md`. Объясняй в ответе существенные проблемы, последствия, причины исправлений и уместные альтернативы; не комментируй каждую строку и не выдавай один допустимый вариант за единственный. Не открывай ответ до самостоятельного решения. Не придумывай отсутствующие контракты или рабочий API.

Для заданий, где исходная цель требует практической проверки поведения, сохраняй имеющийся способ проверки либо используй отдельную среду, если исходник нельзя безопасно подключить. Не добавляй UI, моки, зависимости и инфраструктуру исключительно ради запуска. Не снимай исходные функциональные требования. Если ответ нельзя проверить в исходном окружении, честно укажи ограничение.

Работай небольшими партиями только в `review`: начни с ранее адаптированных задач; после пилота выбирай следующие по фактическому несоответствию. Не изменяй другие категории, сохранённые попытки и несвязанные файлы. Независимое ревью требуется для спорных контрактов и решений, а не для каждого механического переноса.

### Создать и подключить задачу

1. Выполни `pnpm task:new`, введи название, выбери раздел и имя рабочего файла.
2. Команда создаёт пустые рабочий файл и его копию в `starter/`, а также `task.md` со ссылкой. Это черновик автора, а не готовое упражнение. Каталог автоматически не меняется.
3. Подготовь условие, стартовый код и нужные дополнительные файлы. После завершения подготовки скопируй полный чистый рабочий набор в `starter/`.
4. Для браузерной задачи добавь метаданные и ленивый загрузчик рабочего компонента в `src/tasks/index.ts`, как в пилотных задачах. Не создавай новый `active.ts` без необходимости. Для консольного задания укажи команду запуска; браузерный компонент необязателен.
5. Проверь запуск, исходное состояние, критерии задания и восстановление. Для обычного кода проверь ESLint, для исполняемого исходника review отдели ожидаемые учебные диагностики от новых дефектов инфраструктуры.

### Проверка изменений существующих задач

До изменения сравни рабочие файлы с `starter/` и проверь сохранённые попытки. Не затирай чужие или личные решения. Сохраняй исходный смысл, файлы источников, подсказки, данные, публичные контракты и предусмотренные проверки. Проверь ссылки, импортируемые модули, сборку и запуск изменённых задач. Подробный порядок перехода старых упражнений описан в [плане миграции](./docs/task-migration.md).

Старые упражнения пока могут использовать `active.ts` и `attempts/current/`. Не меняй их автоматически только ради структуры.
